# Owner-task benchmark CPU audit

This review concerns `scripts/bench_operator_overhead_owner.py` at `569c890`, with the corrected host guard from `aac3e85`. It compares the runner against the preceding lane runner. It does not modify runtime code, launch a GPU, or interpret uninspected performance results. The exact source hashes and CPU findings are retained in `results/operator_owner_benchmark_audit_v1/qualification.json`.

## Candidate and complete-call contract

The owner mode is exactly the previous lane configuration list plus six owner points: chunk256/512/1024 × N32/N64, threads128. B3 has 61 configurations and B4 has 93; every previous configuration dictionary, candidate identity and source mapping is preserved. `splits=64` is only API compatibility and does not define task boundaries. The candidate name includes both chunk length and tile size. Owner source hashes include its wrapper, CPU task planner and Triton kernel.

`Bound.run()` calls `op(q,k,v)`. Owner `Attention.__call__` launches the task producer, then the merge, and returns BF16 O and natural-log FP32 LSE. The all-empty case skips the producer but still runs the zero/-inf merge. The graph therefore contains the complete GPU operation, not only producer work. Original fixed/native/partition/hierarchy/dynamic calls retain their existing full-call contracts. O and LSE must pass the unchanged FP64 tolerances before a configuration can enter timing selection.

An independent CPU probe of the actual selection block confirms that `best_owner_control` excludes only the owner family. It includes native E0, fixed union/E1 and E4, dynamic v2/v3/emptyguard, FullCol, persistent, wide FullCol, all four prequalified static-v4 points and lane. Hot and cold controls are selected independently. Owner has paired ratios against this strongest required non-owner control and against lane, persistent, v4, FullCol and wide. No stronger prior family disappears when owner is added. This is the strongest control in the measured bounded grid, not a claim of exhaustive kernel tuning or complete PAT/QUILT reproduction.

## Preparation and storage accounting

The outer `prepare_ms` covers RegionPlan construction, import, task planner/descriptor construction, upload, allocation, constructor synchronization and wrapper bookkeeping. Owner `operator_prepare_ms` and `operator_metadata_ms` are separately retained, as is the RegionPlan preparation time. First Triton JIT is outside the owner constructor and is included in `initialization_ms_including_jit`, which covers construction plus the first full producer/merge call and synchronization. Every configuration wall time and family search wall time includes compilation, qualification, warm-up/capture, timing and failures.

Three fresh warm constructions plus a synchronized full call are measured for selected methods. Their preparation and prepare-plus-one-call wall times are separate from GPU event latency. Reuse counts 1/16/64/256 are explicitly hypothetical amortization scenarios. They are not measured request lifetimes. The benchmark does not separately measure topology-change graph recapture or charge recapture inside the steady-state graph. Initial graph work is present in search wall time; a lifecycle claim needs its own explicit capture/rebuild/recapture measurements. The summed `metadata_ms` mixes RegionPlan preparation scope with the owner CPU planning scope, so it must not be renamed a pure CPU-compute statistic.

Owner `workspace_bytes` includes packed FP32 U/M/L, task descriptors, merge indices/counts and output/LSE. Its buffer breakdown, task count, packed rows and full operator metadata are retained even if a later run/qualification step fails. RegionPlan GPU bytes are reported separately. Legacy dynamic controls retain their U/M/L-only convention, native wrappers report their reserved workspace, and E1 wrappers have their existing conventions. These are not equal-scope peak-memory measurements: allocator/graph/compiler caches and CPU topology lists are not all included. Any memory comparison must use the per-row scope/breakdown or reconstruct a common accounting boundary. The source code does not justify a percentage peak-memory claim from the raw workspace column alone.

## Timing and uncertainty

Hot graphs contain 20 complete calls and event time is divided by 20. Cold graphs contain one complete call; a flush allocation of at least twice reported L2 capacity, with a 256 MiB minimum, is updated before the event interval on the same stream. Flush time is excluded. This is a cache regime, not a measurement of HBM traffic.

Each of 20 default blocks measures all selected methods in a randomized order and then the exact reverse. A separate fixed-union A/A graph is included. The 10,000-draw bootstrap resamples entire blocks and keeps both directions together; it computes the median of paired per-direction latency ratios. This is a reasonable within-capture timing-noise interval, conditional on the selected configurations and that hardware/run. It is not a cross-document/capture effect interval, a lifetime/JCT interval, or a correction for multiple comparisons. Block dependence, drift and the A/A result should be inspected; neither CUDA events nor replay mutations become independent documents. Tuning uses separate timing calls before final blocks, but the selected per-capture winner remains a hindsight oracle, and search is explicitly not free.

## Required result-consumption gates

`required_methods` demands at least one successful configuration per family. The time budget can truncate a grid after every family has a winner; a summary may then exist while `tuning_complete` is false. Conversely, `tuning_complete=true` means every planned configuration was attempted, not that every attempt succeeded. A complete-grid claim must check planned/completed counts, `tuning_complete`, every configuration's status and numerical qualification, missing-family lists and external job termination. Failures and incomplete grids must remain visible. Source hashes are checked again at a successful end; interrupted jobs need the surrounding frozen-source/job ledger evidence.

The immutable owner topology is an explicit limitation. Original Q/K/V/Indices values can change in place, but topology changes require rebuilding descriptors and graph recapture; `graph.replay()` bypasses host checks. The corrected host guard is not a content checksum. This runner also does not complete uniform/chunk × rectangular/packed causality or establish application benefit.
