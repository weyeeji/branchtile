# Dynamic-cut two-document production result and audit

The completed original dynamic-cut production run reused one production graph bank across eight document groups (two fixed training documents under ABBA). The independent CPU audit passed all eight exported runs, the immutable source and generated CUDA hashes, document-specific qualification, same output tokens/finish/APC/request trajectories, native S, and recomputed UUID-verified energy counters. `results/raw_pair_multidoc_production_final_audit_v1.json` is the final audit; earlier interim files do not contain a terminal performance conclusion.

After the common engine has initialized, charge the candidate's 2.4392 seconds of offline validation/configuration/single capture once to the first two-document task. Include document switching, cold anchors, group control, generation, worker exports, all NVML samples, and energy identity initialization on both sides. The resulting measured component sums are **211.5299 seconds native versus 195.2285 seconds candidate: 1.08350×, or 7.71% less time**. Generation alone is 1.12957×; that is a narrower metric. Full-task native AA is 1.00112×. Adding the common 52.5776 seconds of measured input preparation and native initialization gives a cold component-sum ratio of 1.06578×, not an independently timed fresh-service experiment.

The one candidate production capture took 2.1914 seconds. Candidate document activation control cost 4.955–9.209 milliseconds, including the control RPC and synchronized cut update; native activation retained its own measured 1.704–4.583 milliseconds and did not upload a candidate cut. This supports the narrow mechanism claim that the same captured bank survived document changes. It does not causally attribute the end-to-end gain to avoiding recapture: a matched old per-document-recapture arm was not measured here. This is the original copied-input dynamic-cut mechanism, not the newer direct-input combination.

Full document-phase cumulative energy was **206,031.8 J native versus 176,322.9 J candidate** across the two GPUs (1.16849× ratio). Counter identities were verified against actual worker CUDA UUIDs. Candidate setup preceded the first sample, so setup Joules are unknown: there is no complete first-use energy claim. CPU energy instrumentation sampling was included in the full-phase metric (27.14 ms native / 26.62 ms candidate per two-document task); initialization was another 1.51 ms on each side.

Single-capture evidence combines one driver capture RPC outside document loops, a worker guard rejecting a second invocation, production-only captured modes, invocation counter one in every exported phase, and a stable device-cut pointer per rank through all eight generations. Every candidate document group had one new full physical-prefix binding; ownership generations advanced and per-document qualified shapes remained isolated. Native transitions leave the candidate cut unchanged but the native path never dispatches it. Physical page IDs and individual slot/epoch arrays were not saved, so this is an audit of the executed frozen checks and receipts, not independent offline reconstruction of every physical page.

The auditor rejects mutated actual receipts with reused generations, changed cut pointers, missing physical rebinding, foreign document IDs or a second capture. It supports the new direct/dynamic variant but that combination still needs its own GPU evidence. Unmeasured Python imports/process launch, the native precision receipt RPC and research parsing/scoring/local-summary writes are outside the stated component sum. One seed, two development documents and same-session ABBA do not establish population or independent-service variability.
