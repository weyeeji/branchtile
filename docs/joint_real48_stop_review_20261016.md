# 真实 48 层 replay：独立复核及停止决定

日期：2026-10-16。结论是 **停止当前 joint-E0 的应用扩展**。本轮证实一个有限、可重复的小正信号；它没有通过预冻的推进门槛，当前准备成本也无法在已观测自然长度内摊销。不能因方向转正，把 1.15× 改成 1.05×，或把完整应用净收益目标改成 attention 子图收益。

本审查在 CPU 上直接读取八个 rank 的 `replay.json`，独立构造配对数组，未调用 root 汇总函数。输入 SHA 全部匹配；**864 个细分格的中位数、配对速度比/差值、10,000 次成簇 bootstrap 区间，与 root 汇总差值全部为 0**。另对主 B3/1% 格枚举全部 `6^6=46,656` 个有序 block 重采样，作为 Monte Carlo 敏感性检查；停止结论不变。计算结果及输入 hashes 见 [独立复核 JSON](../results/platform/joint_real48_independent_recheck_20261016.json)，原始数据见 [root 汇总](../results/joint_real48_replay_v1/analysis/summary.json)。没有运行 GPU、读取正式 eval100/事实审阅内容或修改 root analysis/PAPER。

## 配对统计支持什么

统计单元是**六个 block**，每个保留 random/reverse 两个相关方向；每方向先取其热 3 次/冷 1 次 sample 中位数。不能将 12 个方向、9,216 条 timing samples、864 个分析格、两次设备副本或 4,608 次数值检查当成独立文档样本。这里只有两个文档、每文档两组设备副本、同一个短 decode 状态。六簇 bootstrap 只描述该固定状态的重复测量不确定性，不提供任务总体或自然轨迹置信界。

主指标固定为 `prepare_plus_48_layers / complete_wall_us / rank_max_proxy / epsilon01 / B3`：

| 文档、设备副本 | hot 速度比 / 配对节省 | cold 速度比 / 配对节省 | CPU+D2H 准备代理 | 回本 B3 步数 hot / cold |
| --- | ---: | ---: | ---: | ---: |
| publicdev1，replica0 | 1.06099 / 118.501 μs | 1.06205 / 120.743 μs | 2.92547 s | 24,687 / 24,229 |
| publicdev1，replica1 | 1.05654 / 110.360 μs | 1.06090 / 119.450 μs | 2.86966 s | 26,003 / 24,024 |
| original，replica0 | 1.05368 / 105.409 μs | 1.05849 / 115.164 μs | 2.84825 s | 27,021 / 24,732 |
| original，replica1 | 1.05488 / 110.950 μs | 1.05160 / 105.001 μs | 2.81332 s | 25,357 / 26,793 |

所有主格速度比和 bootstrap 上界都低于 **1.15**。八格 A/A（epsilon0 对 independent）中位速度比范围 **0.997426–1.002846**；因此不能简单把主结果全部解释成 A/A 偏移。但通过噪声辨识不等于通过幅度门槛。1.0516–1.0621× 对应约 **4.91%–5.84% 调用延迟降低**，不是 5%–6% 模型 JCT 改善。两次设备副本同方向是有价值的稳定性证据，不产生新文档。

数值方面，4,608 个 same-active-mask SIMT 检查全部通过，epsilon0 输出位相等；这是各自支持集上的执行资格，**不是改 mask 后的输出/任务质量等价**。B1 的速度比接近 1；B2 有较小正信号，但它们是 B3 前一/两行，不能当成真实退出后仍存活的请求。`rank_max_proxy` 对两个分别测量的 rank 取最大值，保留其名字：不是实测 TP critical path，不能从 NCCL/模型 JCT 机械减去这个差值。真实 48 层 KV/Q/layout 和生产 `output.copy_` 被保留，层间 MoE/GEMM/TP 交错没有被 replay；cold 的 256 MiB flush 也不是自然模型的缓存状态。

## 准备成本仍决定停止

这里使用本轮记录的 `P=max_rank(CPU_finalize_epsilon01 + score_D2H_and_copy)`，不把 TP 两 rank 相加，不减 epsilon0 验证费用，也不把三个 epsilon 的 8.3–8.6 s RPC 总时间计到部署一个 epsilon。D2H 在完整 selector 时间中只能记一次。单配置 P 为 **2.813–2.925 s**；独立安装与 joint 安装都约 0.63–0.65 s，逐 block/direction 配对安装差异仅约毫秒，单列后回本结论不变。它仍不是单配置服务 RPC 的实测关键路径，也未给未来更快 CPU 实现收益信用。

自然长度只取已有 E0 同栈输出的 token **计数**，不看答案文本，也不借用 joint/union 变长输出来创造摊销机会：

| 文档 | E0 三题长度 | 共同 B3 步上限 | 最长请求步上限 | 极乐观全生命周期毛节省 |
| --- | --- | ---: | ---: | ---: |
| original | 1144、1138、1140 | 1138 | 1144 | 0.144 s |
| publicdev1 | 4003、1774、1883 | 1774 | 4003 | 0.613 s |

最后一列刻意采用每文档两副本/冷热中最有利的 **exact block-bootstrap 节省上端**（126.261/153.135 μs），并将 B3 节省不合理地延伸到全部 B2/B1 步；准备取同文档较小 P。即使如此，毛节省仍显著小于 2.813/2.870 s。它是有意偏乐观的**条件外推**，不是硬件上界、统计联合区间或实际 joint 轨迹预测。prefill 生成首 token 时实际 decode 步还更少。即便臆设全部 8192 个步都保持本轮最有利 153.135 μs 节省，也只有约 1.254 s，仍不足当前 P。

若只在共同 B3 期间获得收益，达到 5% 的 anchor+generation 改善，需要每完整步省 **3.368 ms（original）/2.756 ms（publicdev1）**，远高于实测约 0.105–0.121 ms；这里使用的 20.390/40.392 s 基线还未含全部初始化/selector，因此也是偏宽松要求。即使把 P 假设为零，仍不能把 attention 子图的百分比直接报告成完整应用改善。

## 决定及边界

[冻结 protocol](../configs/joint_real48_replay_protocol_v1.json) 明确要求 1.15×、超过两倍 A/A 噪声、应用 5% 目标，并规定本次诊断后不扩自然 pilot、不重试/搜索布局。**因此归档当前 joint-E0 主张，停止其完整应用扩跑与为挽救门槛而加的新机制。** 保留“相同每请求 k、共享物理地址、改变支持集后，固定快照完整 48 层调用存在小幅正收益”的有限观察，不写成已成功的系统加速贡献。全源 KV 仍保活，物理容量收益仍为零；质量不稳定也未被本轮解决。

这不是证明所有 joint-selection 方法都无价值。一个未来新研究必须事先提供不同的、可证伪的机制和资源/质量依据，重新冻结实验，而不能把未实现的 selector 加速、不同真实存活组合或更长回答当成现有系统已经拥有的收益。当前结果不支持继续扩大这条实现路线。
